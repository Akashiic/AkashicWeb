# Running a CEF browser inside GTNH 1.7.10, and what AkashicFM can give

> Research stream `04-gtnh-integration`, produced 2026-10-05..10 by a research agent in a Linux cloud container. Raw output: [`raw/04-gtnh-integration.json`](raw/04-gtnh-integration.json). Paths such as `/home/user/...` or `scratchpad/...` refer to that container and do not exist in this repository; the reusable probe sources are under [`/spikes`](../../spikes).

Java/LWJGL variants of GTNH (Java 8 + LWJGL2, lwjgl3ify 2.x GLFW, lwjgl3ify 3.x SDL3), Angelica rendering rules, threading, input, packaging, and the AkashicFM audio bridge.

## Errata and corrections

- CORRECTION (technical critique, stream 08): Angelica's TileEntityRenderBoundsRegistry exists only in Angelica 2.x (GTNH 2.9 RC). It does not exist in 1.0.0-beta66b (GTNH 2.8.4). Call it reflectively and tolerate ClassNotFoundException.
- CORRECTION (stream 08): java.nio.DirectByteBuffer(long,int) does not exist on Java 21 (it is (long,long)). Prefer a native NewDirectByteBuffer per channel for the audio DataPointer.

## Summary

The client stack depends on the GTNH version. GTNH 2.8.4 (stable) ships lwjgl3ify 2.1.16, whose window layer is GLFW, plus Angelica 1.0.0-beta66b. GTNH 2.9.0 is still a release candidate (RC-2 dated 2026-10-04) and ships lwjgl3ify 3.0.37, which uses SDL3, plus Angelica 2.2.28. Angelica 2.x needs a GL 3.3 core profile and routes every GL call a mod makes through GLStateManager, which emulates the old fixed-function pipeline. Angelica is in both the Java 8 and the Java 17+ packs; lwjgl3ify is only in the Java 17+ packs. GTNH publishes both Java 8 and Java 17-25 downloads and its build tooling now names them Java_17-26, so the WD port has to work on Java 8 with LWJGL2, on lwjgl3ify 2.x and on lwjgl3ify 3.x. No public data says which Java the players use, so the owner should measure it on his own server.

On the browser engine: the prebuilt jcefmaven natives (CEF 152.0.6, Chromium 152.0.7977.83, Java 8 bytecode) work, but upstream JCEF needs AWT. It loads jawt, runs init and the message pump on the Swing event thread (onPaint arrived on AWT-EventQueue-0 in a probe run in this container), and has no CefAudioHandler at all, so audio cannot be captured for positional playback. The CCBlueX java-cef fork is on the same CEF 152, has no AWT dependency and does have CefAudioHandler, but its native key, mouse and wheel code looks up org/lwjgl/sdl/* classes, its DataPointer needs the LWJGL3 MemoryUtil class, and its audio_handler.cpp uses raw FindClass calls. The CinemaMod fork has the same problems with GLFW instead of SDL and is stuck on Chromium 116. The workable route is to build our own natives from the CCBlueX fork with its public CI, Windows x64 and Linux x64 only, after a few small native patches. macOS looks out of reach by Oct 25: lwjgl3ify forces java.awt.headless=true there and runs the game off the main thread, while CEF on macOS must be initialized on the main thread.

For rendering, upload frames only on the client render thread, once per frame and outside the TESR (shaderpacks render tile entities again in the shadow pass). Use BGRA with GL_UNSIGNED_INT_8_8_8_8_REV through GL11 calls in the mod's own classes, which Angelica redirects, and reset UNPACK_ROW_LENGTH/SKIP and any PBO binding afterwards, because Angelica beta66b only caches texture binds. CEF frames have to be copied out of onPaint: about 0.5-1.1 ms per 1080p frame in the probe.

AkashicFM's audio engine fits well. The CEF audio packets get converted to 48 kHz stereo 16-bit and wrapped as an AudioFeed, then passed to AudioEngine.touch with LEFT/RIGHT EmitterSpecs, GainModel gains and OcclusionField occlusion; EFX low-pass and reverb follow automatically. Three AkashicFM changes are needed first: RadioAudioController currently stops other mods' playbacks every tick (retainOnly/stopAll/room), PcmRing.write blocks when full, and Playback's queue of about 1 s lets lip-sync drift after a game hitch. The relay's timed-feed mechanism can fix the drift. ToolManager is a good starting pattern for the natives download but needs pinned hashes, multi-file extraction with path checks and bigger size limits: libcef.so alone is 267.9 MB, above its 250 MiB cap. Nothing here was built or run in-game; the only runtime numbers come from a headless Linux probe in this container.

## Open questions

- Which GTNH version (2.8.4 stable or 2.9.x) and which Java variants (8 vs 17-25) does the owner's server and its players actually run? A login handshake reporting java.version, lwjgl3ify version and OS would answer this within days.
- What share of the player base is on macOS or Linux/Wayland? This decides whether the macOS fallback and the Linux test are enough.
- Does CEF loopback audio capture (CefAudioHandler active) mute Chromium's normal output in CEF 152 on Windows and Linux? This was not tested here; if it does not, the sound is heard twice (OS output plus OpenAL).
- Can the CCBlueX java-cef workflow, forked with our native patches (plain-int input, NewDirectByteBuffer audio, helper FindClass, params read-back, Windows job object), produce green windows-amd64 and linux-amd64 builds within about a week? This has not been attempted.
- Is the CEF pts (TimeTicks) on the same clock as Java's System.nanoTime on Windows (QPC) and Linux (CLOCK_MONOTONIC), or does the offset have to be estimated per stream? This affects the timed-feed design.
- Will the chosen live source (presumably a YouTube live channel) play in a CEF build without proprietary codecs (H.264/AAC)? This belongs to the codec research, but it determines whether any of this pipeline matters for the Oct 25 stream.
- Does Angelica 2.x run on the Java 8 pack with a core-profile context on the players' GPUs, and does a glTexSubImage2D BGRA upload of 720p every frame stay within budget there? Nothing was run in-game in this research.
- Can AkashicFM accept the small API change (an external audio source provider plus per-feed latency/clock overrides)? Both mods belong to the owner, but AkashicFM is at 1.2.0 with its own release gates.
