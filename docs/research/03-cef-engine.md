Paths such as `/home/user/...` or `scratchpad/...` refer to that container and do not exist in this repository; the reusable probe sources are under [`/spikes`](../../spikes).

java-cef upstream, jcefmaven, CinemaMod MCEF, CCBlueX java-cef; OSR rendering, audio handler, codecs, resource cost. A Java 8 OSR probe was run in a Linux container.

- ERRATUM: "no reachable JCEF build plays H.264 or AAC" is superseded by stream 05: OBS hosts codec-enabled CEF 150 builds, and CCBlueX java-cef compiled against the OBS Linux build played H.264/AAC (VERIFIED, Linux only).

## Summary

The biggest risk is codecs: no reachable JCEF build plays H.264 or AAC, so YouTube live and Twitch are expected to fail on a stock build. Upstream java-cef (chromiumembedded/java-cef, HEAD 17e805a, 2026-09-09) tracks CEF 152.0.6 / Chromium 152.0.7977.83, and its Java code is Java 8: build.xml targets 1.8, and the jcef-api jar on Maven Central has 204 classes at major 52, built by JDK 1.8.0_504. jcefmaven 152.0.6 (2026-09-30) wraps that jcef-api; its own jar is also major 52 and its README says Java 8+. Natives exist for linux amd64/arm64/arm, windows amd64/arm64/i386 and macOS amd64/arm64, at 140-171 MB per platform (360 MB extracted on Linux x64). They are fetched from GitHub releases with Maven Central as fallback, with no checksum check and no tar path-traversal check. Upstream OSR delivers a BGRA ByteBuffer through onPaint with dirty rects, valid only during the callback. Upstream has no onAcceleratedPaint (PRs #524/#547 still open) and no CefAudioHandler. CefBrowserOsr is package-private and wired to JOGL, initialization and pumping run on the AWT EDT, and the Chromium sandbox is always disabled. I built a test harness that proves the unmodified jcef-api 152 jar works without JOGL. It uses a custom OSR class in package org.cef.browser, compiled with --release 8, and rendered 1080p VP9/Opus at 29.7 fps (30 fps setting) and 59.3 fps (60 fps setting) with paints arriving on AWT-EventQueue-0. In this container CEF 152 also needed --no-first-run, failing otherwise with exit code 28. The same run showed AAC, H.264, HEVC and MPEG-TS unsupported, while VP9, AV1, Opus, MP3 and Vorbis were supported, and a local H.264/AAC MP4 failed with MediaError 4. The CEF maintainer confirms proprietary codecs are off by default in standard builds (issue #3559, an OS-decoder-only option, is still open), and the CinemaMod and CCBlueX forks use the same codec-free distributions. Community format docs and many MCEF/WebDisplays user reports point to YouTube live (AAC-only audio) and Twitch failing for this reason. I could not confirm that against a real YouTube live because YouTube bot-walled this datacenter IP. Fixing it means building CEF from source with proprietary_codecs (at least 16 GB RAM, 150 GB disk, about 4 h per build) plus Via LA AVC/AAC licensing, or an owner-run VP9/Opus relay. CinemaMod MCEF is stale: java-cef fork eaeb3d4 is on CEF 116 (2023), capped at 30 fps, Java 21/GLFW only, with --disable-web-security on, arm64 builds that are really x86_64, and a 'checksum' that never hashes the archive. Its useful parts are render-thread pumping, dirty-rect glTexSubImage2D upload, and a fork-level CefAudioHandler that delivers planar float PCM through a DataPointer that needs LWJGL3. CEF mutes the page while capturing audio, so the mod has to play the PCM itself, for example through AkashicFM's OpenAL engine. The best maintained base is CCBlueX/java-cef (2026-10-02), which is current at CEF 152 with an audio handler, accelerated paint and a Linux pump fix, but its natives are hosted on LiquidBounce servers, so they would need to be rebuilt and self-hosted. Accelerated paint there depends on EXT_memory_object_win32 (Intel unsupported, older AMD drivers leak) or EGL dmabuf, so it does not fit 1.7.10. Widevine is only fetched at runtime by Google's component updater, and EME failed in the probe, so DRM sources such as Globoplay should be assumed not to work. On a 4-vCPU container with software decoding, one browser cost about 0.43 GiB PSS when idle and about 0.54 GiB during 1080p30 playback, using about 40% of one core at 1080p30 and about 70% at 1080p60, before Minecraft's own GL upload. On latency: the browser adds only tens of milliseconds, but YouTube live sits 2-60 s behind, set by the broadcaster, and players are not in sync with each other, so 'almost no ms' is not achievable.
