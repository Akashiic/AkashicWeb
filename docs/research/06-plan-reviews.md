# Adversarial reviews of the first plan

> Two independent review agents attacked the first plan ([`raw/06-plan-kiosk-scope.json`](raw/06-plan-kiosk-scope.json)) on 2026-10-10. That plan was written for a locked, admin-only "kiosk" telão. The owner later rejected the kiosk scope (see [`../DECISIONS.md`](../DECISIONS.md) D-002), so findings about presets, the relay as primary, or a client-only display apply only where [`../PLAN.md`](../PLAN.md) still uses them. Raw: [`raw/07-critique-feasibility.json`](raw/07-critique-feasibility.json), [`raw/08-critique-technical.json`](raw/08-critique-technical.json).

## Feasibility and completeness review

**Verdict.** NOT FEASIBLE AS WRITTEN. It can be rescued by re-ordering decisions and cutting scope, but the 65-75% figure has no basis (INFERRED). Working backwards from a failure on 2026-10-25, these are the most likely causes, in order:
(1) Rights fall through late. The final rights decision is on 10-21, after RC1 and the natives prefetch (10-20). If no broadcaster grants relay permission, which is likely in 10 days around an election, the only path left is the YouTube embed. That path needs the codec build, and the codec build may not have been shipped. So the relay, which the plan calls "PRIMARY", is probably the path that will be legally unusable.
(2) Staffing. The plan assumes two parallel developers, but the evidence shows one author working with an AI assistant. Every Windows test needs the owner's own PC. The AI assistant already lost 5 days to usage limits, and the schedule has zero slack.
(3) Field defects surface at the first public rehearsal (G4, 10-18). That leaves too little time for a native rebuild plus a re-download of 150-350 MB by players. The Akashic track record shows automated and Linux-only gates repeatedly miss field defects.
(4) Adoption. The block-based design makes the mod REQUIRED to join. Players who did not update by 10-25 cannot enter the server on election night. The public rehearsal (10-18) also happens before the mod is published to players (10-20).
(5) A single point of failure on election night. The owner is at once the ingest operator, the restreamer, the admin and the decision maker, on one home PC. The relay endpoints are also public and have no authentication.
Fix order:
- Decide on 10-11/10-12: the source, its embeddability, and the codec build. Ship the codec build as the default engine if any candidate source is YouTube-only.
- Make the telão a client-side display anchored to coordinates the server sends, so vanilla clients still join, or prove that clients without the mod can join.
- Freeze the natives at G1 and push the installer from about 10-15 in a small early client release.
- Plan for one developer: no relay unless a rights-clean source is confirmed, and no admin keyboard, Linux tier or LL-HLS steering.
- Add per-player relay tokens, a server kill switch, a crash-loop guard, a separate ingest machine and a no-restart window on the 25th.
Nothing in this review was built or run. All findings come from reading repositories and the plan.

## Technical claims review

**Verdict.** The plan's main technical choices hold up when checked against code and artifacts: the CCBlueX java-cef engine, Java 8 bytecode, the OBS CEF 7871 codec build and the relay. I found no blocker. Eight claims are wrong, overstated or only partly checked, and four of them change the work: (1) The Angelica render-bounds registry the plan calls a "VERIFIED requirement" does not exist in Angelica 1.0.0-beta66b, which ships with the recommended GTNH 2.8.4. It exists only in Angelica 2.x, which ships with GTNH 2.9. (2) Linux natives built by the forked CCBlueX CI on ubuntu-24.04 need GCC 13's libstdc++ (GLIBCXX_3.4.31) and glibc 2.34. The plan's "glibc 2.31+" support tier is therefore wrong. (3) The plan to rename the helper is silently undone: CCBlueX CefApp.initialize() always sets browser_subprocess_path to jcef_helper(.exe), so the Java side needs a patch too. (4) Downloading OBS's raw CEF on each player's machine does not fit the plan's own size caps. Linux libcef.so is 2.03 GB unstripped, and the Windows zip unpacks to 1.20 GB, mostly OBS build leftovers. A repackaged (and therefore Akashic-redistributed) bundle is needed, or selective extraction plus a Linux exception. Smaller corrections: CCBlueX still uses AWT and Swing classes; the DirectByteBuffer(long,int) fallback does not exist on Java 21; a custom OSR class is unnecessary; the Windows OBS-150 build is non-standard and still untested; the latency numbers came from a muted-autoplay localhost harness with no saved output. Everything not listed as confirmed remains unconfirmed. Not run: any Windows build, anything in-game, any WAN test, the stock CEF 152 WebRTC runtime.
